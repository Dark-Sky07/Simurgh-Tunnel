# 🕊️ سیمرغ تونل

[English](README.md) · **فارسی** &nbsp;|&nbsp; [نصب](#نصب) · [تنظیمات](docs/CONFIGURATION.fa.md) · [عیب‌یابی](docs/TROUBLESHOOTING.fa.md) · [English](README.md)

<div dir="rtl">

یک **تونل شفاف و چندگانهٔ TCP/UDP** بین یک یا چند سرور ایران (رله) و یک یا چند
سرور خارج (اگزیت) — هم‌خانوادهٔ کاریز / رتهال / frpulse، ساخته‌شده برای شرایط
شبکهٔ ایران.

کاربران شما **همان کانفیگ فعلی‌شان** را نگه می‌دارند (3x-ui، OMEGA، X-UI، Xray،
هر چیزی که روی TCP کار می‌کند) و فقط آدرس سرور را به **IP سرور ایران** تغییر
می‌دهند. ترافیک از داخل یک تونل استتارشده به سرور خارج می‌رسد و آن‌جا دقیقاً
مثل قبل تحویل داده می‌شود.

```
کاربر ──همان کانفیگ، IP ایران──► [رلهٔ ایران] ══یک تونل استتارشده══► [اگزیت خارج] ──► 127.0.0.1:پنل
```

## چرا برای ایران مناسب است

| نیاز | کار سیمرغ |
|---|---|
| IP و دامنهٔ سرور خارج فیلتر نشود | کاربر فقط **IP ایران** را می‌بیند؛ آدرس خارجی هرگز در کانفیگ، QR یا لینک اشتراک کاربران دیده نمی‌شود. |
| DPI تشخیص نده | یک اتصال TLS واقعی به دامنهٔ واقعی: گواهی معتبر، SNI درست و **سایت طعمه** (صفحهٔ nginx) برای هر کسی که توکن ندارد. |
| سرعت و پایداری | یک اتصال چندگانه (`mux`) برای همهٔ کاربران و همهٔ پورت‌ها؛ بدون رمزگذاری دوبارهٔ ترافیک کاربر، با کنترل جریان مبتنی بر اعتبار به‌جای بافر کردن. پنجرهٔ هر استریم روی مسیرهای طولانی **خودش رشد می‌کند** و با `connections = 2..16` یک استخر تونل نگه داشته می‌شود تا نه یک فلوی TCP و نه قطع‌شدن یک تونل، سقف سرعت همه نشود. |
| نصب آسان | یک فرمان روی هر سرور و یک لینک برای انتقال کانفیگ. |
| کم‌مصرف | پایتون ۳.۹+ + asyncio، بدون Node/Go/دیتابیس (روی ۳.۹/۳.۱۰ خوانندهٔ TOML همراهِ خودش است، پس نصب به PyPI نیاز ندارد). رم در حالت بی‌کاری حدود ۲۵ تا ۴۰ مگابایت. |
| منوی متنی + پنل وب | **منوی متنی کاملاً انگلیسی** (`simurgh menu`) و **پنل وب دوزبانه (انگلیسی/فارسی)** با نمودار زنده. |

## دو حالت کار

* **مستقیم (پیش‌فرض)** — رلهٔ ایران به اگزیت خارج وصل می‌شود؛ سرور خارج باید یک
  پورت ورودی باز داشته باشد (مثلاً TCP 443).
* **معکوس** (`dial = "exit"`) — **سرور خارج به رلهٔ ایران وصل می‌شود.** برای وقتی
  که سرور خارج NAT است، پورت ورودی ندارد، IP عوض می‌شود یا نمی‌خواهید هیچ پورتی
  روی آن باز باشد. در هر دو حالت، پورت‌های کاربران روی سرور ایران باقی می‌مانند.

## نصب

### یک دستور برای هر سروری

روی **سرور خارج** و روی **سرور ایران** دقیقاً **همین دستور** را اجرا کنید:

```bash
curl -fsSL https://raw.githubusercontent.com/Dark-Sky07/Simurgh-Tunnel/main/install.sh | sudo bash
```

نصاب همه‌چیزِ لازم را نصب می‌کند (محیط پایتون، موتور کامپایل‌شده وقتی ساخته
شود، سرویس systemd و تنظیمات کرنل) و نقش سرور را خودش تشخیص می‌دهد:

* **آدرس IP ایرانی ← رله (سرور ایران).** نصاب آدرس سرور خارج (`IP:port`) و
  توکنی که سرور خارج در پایان نصبش چاپ کرده را می‌پرسد.
* **هر کشور دیگر ← اگزیت (سرور خارج).** در پایان توکن و لینک اتصال را چاپ
  می‌کند. وقتی سرور ایران توکن را خواست، همان را وارد کنید.

اجرای دوباره‌ی دستور، نقش فعلی سرور را نگه می‌دارد. گزینه‌هایی مثل `--role`،
`--name`، `--listen` و `--mapping` اختیاری‌اند؛ برای دیدن همه‌شان
`bash install.sh --help` را اجرا کنید.

### سرور ایران (رله) — حالت معکوس

```bash
sudo bash install.sh --role relay --dial exit --tunnel-port 8443 --token XXX
# سپس روی سرور خارج، لینکی که `simurgh link` چاپ کرده را وارد کنید:
sudo simurgh join 'simurgh://<iran-ip>:8787/setup?u=admin&p=…#ir-tehran'
sudo simurgh restart
```

### هر دو نقش روی یک سرور

با `--role both` رله و اگزیت با هم نصب می‌شوند؛ رله به اگزیت محلی روی
`127.0.0.1:443` وصل می‌شود — یعنی اولین پورت `--listen`؛ پس با
`--role both --tunnel-port 8443` اگزیت هم روی همان ۸۴۴۳ گوش می‌دهد (یک توکن
مشترک برای هر دو سرویس ساخته می‌شود):

```bash
sudo bash install.sh --role both --name my-server
sudo bash install.sh --role both --tunnel-port 8443    # تونل روی ۸۴۴۳
```

در حالت معکوس (`--dial exit`) نصاب خودش اگزیت محلی را به رله وصل می‌کند؛ اگر پنل
هنوز بالا نیامده باشد، همان دو فرمان لازم را چاپ می‌کند.

اجرای مجدد نصاب بی‌خطر است: کانفیگ را تازه می‌کند، پس بعد از آپدیت یا تغییر
شبکه می‌توانید دوباره اجرا کنید (`--uninstall --purge` هم همه‌چیز را پاک می‌کند).

### کاربران

فقط آدرس سرور را در کانفیگ‌شان از IP/دامنهٔ خارجی به **IP ایران** تغییر دهید.
پورت، رمز، TLS، SNI و بقیهٔ تنظیمات دست‌نخورده می‌مانند.

## فرمان‌های روزمره

```bash
simurgh menu                     # منوی متنی انگلیسی (پیشنهادی برای شروع)
simurgh status                   # وضعیت تونل، ترافیک، پینگ، پورت‌ها
simurgh mapping add 443 443      # پورت ایران -> پورت سرور خارج
simurgh mapping list | remove | toggle
simurgh speedtest                # سرعت واقعی از داخل تونل
simurgh logs -f                  # لاگ زنده
simurgh doctor                   # عیب‌یابی خودکار با راهنمای عملی
simurgh update --check           # نسخهٔ جدیدتری آمده؟  (--force برای نصب دوباره)
simurgh link --show              # لینک اتصال برای سرور دیگر
simurgh join '<link>'            # ساخت کانفیگ از روی لینک
simurgh start | stop | restart   # کنترل سرویس (systemd)
simurgh uninstall --purge        # حذف کامل
```

مرجع کامل: [docs/CONFIGURATION.fa.md](docs/CONFIGURATION.fa.md).

## پنل وب (دوزبانه)

`http://<iran-ip>:8787` — انگلیسی **و** فارسی (دکمهٔ `EN / فا`، انتخاب هر مرورگر
ذخیره می‌شود، چیدمان راست‌به‌چپ/چپ‌به‌راست خودکار). وضعیت زندهٔ تونل، نمودار
سرعت، افزودن/حذف/خاموش‌روشن کردن پورت‌ها **بدون ری‌استارت**، تست سرعت، لاگ زنده،
ری‌استارت سرویس و لینک اتصال. ورود یک‌کلیکی:
`http://<iran-ip>:8787/?k=رمز-پنل`. همه‌چیز از خود سرور سرو می‌شود؛ نه CDN، نه
فونت خارجی.

> هر چیزی که اپراتور سرور بیرون از پنل می‌بیند — منوی متنی، CLI و خروجی نصاب —
> **فقط انگلیسی** است.

## دو موتور، یک پروتکل

سیمرغ دو پیاده‌سازی از یک پروتکل دارد و هر طرف تانل می‌تواند هر کدام را
اجرا کند:

| موتور | چیست | کِی استفاده شود |
|---|---|---|
| `go` *(پیش‌فرض)* | موتور دادهٔ کامپایل‌شده: یک گوروتین برای هر کاربر، استفاده از همهٔ هسته‌ها، حدود ۸ برابر CPU کمتر به ازای هر گیگابایت | پیش‌فرض هر جا باینری نصب شده باشد |
| `python` | موتور مرجع، فقط کتابخانهٔ استاندارد پایتون | جانشین خودکار وقتی باینری موجود نیست، و مرجع پروتکل روی سیم |

`simurgh init` وقتی این ماشین باینری را داشته باشد `engine = "go"` می‌نویسد و
وقتی نداشته باشد `engine = "python"` (`--engine go|python` هر کدام را
تحمیل می‌کند، و نصاب اول باینری را دانلود یا کامپایل می‌کند). تغییر بعدی یک
دستور است:

```bash
sudo bash tools/build-go.sh     # اگر Go نصب نباشد خودش نصب/دانلود می‌کند
simurgh engine go               # نوشتن engine = "go" در relay.toml / exit.toml
simurgh restart
```

بقیهٔ چیزها تغییر نمی‌کند: پنل، منوی متنی و CLI همان پایتون می‌مانند، همان
فایل‌های کانفیگ را می‌خوانند و اعداد زندهٔ پنل از `state.json` می‌آید که هر دو
موتور می‌نویسند. تفاوت را همین‌جا ببینید:

```bash
python tools/latency_bench.py 60 80 plain              # موتور پایتون
go/bin/simurgh-go bench -mb 256 -delay 20 -streams 64  # موتور Go با ۶۴ کاربر
```

## حامل‌ها (نوع استتار)

| حامل | شبیه چه چیزی است | کِی استفاده شود |
|---|---|---|
| `tls` (پیش‌فرض) | یک سایت HTTPS واقعی با صفحهٔ طعمه | تقریباً همیشه |
| `wss` | همان، روی ارتقای WebSocket | وقتی فقط WebSocket مجاز است |
| `raw` | نویز تصادفی + X25519 + ChaCha20-Poly1305 | وقتی خود TLS مشکوک است |
| `plain` | TCP + هدر HMAC | دو سرور مطمئن/داخلی |

هر دو موتور هر چهار حامل را پشتیبانی می‌کنند و روی هر چهار حامل با هم حرف
می‌زنند (رلهٔ Go با اگزیت پایتون و برعکس، هر دو بخشی از تست‌ها هستند). حامل
`raw` در موتور پایتون به پکیج `cryptography` نیاز دارد (`pip install
'.[secure]'` که نصاب خودش نصب می‌کند)؛ در موتور Go پیاده‌سازی
ChaCha20-Poly1305 به‌صورت vendor داخل `go/third_party/` است، پس بیلد آن نه
شبکه می‌خواهد و نه پکیج.

## امنیت

* هدر ۲۵ بایتی دست‌دادن (نسخه، زمان، HMAC-SHA256[:16]) با بازهٔ ±۱۸۰ ثانیه و
  کلید `sha256("simurgh/v2/token|" + token)`؛ کش ضدتکرار ۳۰۰ ثانیه‌ای جلوی
  تکرار دست‌دادن‌های ضبط‌شده را می‌گیرد.
* بدون توکن، شنونده مثل یک وب‌سرور عادی پاسخ می‌دهد (صفحهٔ طعمه)؛ کسی که
  کنجکاو باشد چیزی نمی‌فهمد.
* گواهی خودامضای اگزیت را می‌توان با **پین اثرانگشت SHA-256** قفل کرد
  (`fingerprint`) یا از گواهی واقعی Let’s Encrypt استفاده کرد.
* بایت‌های اول هر اتصال در یک سگمنت TCP جدا می‌رود (`split = 3`، پیش‌فرض نصب):
  دستگاهی که ترافیک را فقط از سگمنت اول دسته‌بندی می‌کند یک قطعهٔ ناقص می‌بیند،
  در حالی که ClientHello واقعی چند میلی‌ثانیه بعد کامل می‌شود. با `--split 0`
  خاموش می‌شود.
* فایل‌های کانفیگ به‌صورت اتمیک و با مجوز `0600` نوشته می‌شوند.

## چیزهایی که در همین مخزن تست شده‌اند

| `go test ./...` (داخل پوشهٔ `go/`) | **سبز** — مالتی‌پلکسر (رفت‌وبرگشت، برگشت کردیت، رد درخواست، پنجرهٔ مشترک) و حامل/طعمه (plain، TLS، توکن غلط، پروکسی `site:`، صفحهٔ دلخواه) |

| سرعت (یک ماشین، لوپ‌بک) | حدود ۳ گیگابیت بر ثانیه دانلود و ۱.۳ گیگابیت آپلود از داخل تونل |

| استخر تونل | ۸ کاربر روی ۴ تونل: ۱۳.۰ مگابایت بر ثانیه در برابر ۳.۶ روی یک تونل با همان سقف هر جریان، پخش بار ۱/۱/۱/۱ |
| موتور Go، همان مسیر ۶۰ میلی‌ثانیه | **۴۲.۳ مگابایت بر ثانیه (۳۳۸ مگابیت)** روی `plain` و **۳۰.۵ (۲۴۴ مگابیت)** روی `tls` (و ۳۰.۴ روی `wss`) |
| موتور Go، مسیر کوتاه | **۳۸۳ مگابایت بر ثانیه (۳.۰۷ گیگابیت)** یک استریم |
| موتور Go، کاربران زیاد | **۴۳۰ مگابایت بر ثانیه (۳.۴ گیگابیت) برای ۶۴ کاربر همزمان روی یک اتصال تونل** و ۵۰۳ مگابایت (۴.۰ گیگابیت) روی دو اتصال — ۲ هسته |
| موتور Go، مصرف CPU | **۰.۶ تا ۰.۸ ثانیه‌هسته به ازای هر ۲۵۶ مگابایت** (رله + اگزیت + کلاینت آزمون در همان پروسه) |
| هم‌کاری موتورها | رلهٔ Go ⇄ اگزیت Python و رلهٔ Python ⇄ اگزیت Go روی `plain` و `udp`: `python -m pytest tests/test_udp_cross_engine.py` یک موتور را رله و دیگری را اگزیت می‌کند و پاسخ واقعی HTTP را بایت‌به‌بایت می‌سنجد — در هر دو جهت |
| حامل `udp` در موتور Go | موتور کامپایل‌شده همان حامل دیتاگرامی را بایت‌به‌بایت با پایتون حرف می‌زند: هلو با HMAC، ChaCha20-Poly1305، بازفرست با SACK، FEC (`fec = "8:2"` واقعاً یک دیتاگرام افتاده را ترمیم می‌کند) و مالتی‌پلکسر روی UDP؛ **۸۰ مگابایت بر ثانیه** در آزمون‌های Go روی لوپ‌بک |
| محدودیت‌ها در موتور Go | `rate_limit`، `quota` / `quota_period` / `quota_action` (`block`، `throttle`، `warn`) و `max_conns` دقیقاً مثل موتور پایتون در مسیر دادهٔ Go اعمال می‌شوند، از همان `relay.toml`، و موتور Go همان فایل `traffic.json` را می‌نویسد — پنل و `simurgh traffic` یک تاریخچه را می‌خوانند، هر موتوری که اجرا شده باشد |
| متریک Prometheus (`/metrics`) | روی همان پورت پنل، متن Prometheus سرو می‌شود (نود، تونل، هر mapping، دفتر کل، کوتا و سلامت استخر)، با همان احراز هویت پنل و از همان وضعیتی خوانده می‌شود که پنل نشان می‌دهد — پس با موتور پایتون **و** Go (`state.json`) کار می‌کند |
| `simurgh update` | خودش نوع نصب را تشخیص می‌دهد: چک‌اوت گیت به جدیدترین تگ می‌رود (و موتور را دوباره می‌سازد)، نصب بسته‌ای فایل مناسب همین ماشین را دانلود و SHA-256 را با `SHA256SUMS.txt` می‌سنجد و اتمیک جایگزین می‌کند (نسخهٔ قبل `.bak` می‌ماند) و نصب pip از pip به‌روزرسانی می‌شود. `--check [--json]` فقط گزارش می‌دهد و بدون اینترنت هیچ‌چیز عوض نمی‌شود |
| مصرف رم | ۳۳ تا ۴۱ مگابایت اوج روی یک استریم پرسرعت و ۹۵ مگابایت هنگام جابه‌جایی ۲۰۰ مگابایت روی ۴ تونل |
| طعمه | HTTP ساده یا TLS + درخواست HTTP → صفحهٔ واقعی nginx (۲۰۰)، مسیر ناشناس → ۴۰۴، کلاینت HTTP/2 → `GOAWAY(HTTP_1_1_REQUIRED)` مثل یک سایت معمولی، `fallback = "site:host:port"` → همان سایت واقعاً سرو می‌شود، توکن غلط → ۴۰۰/نویز یا قطع بی‌صدا |
| خودترمیمی | با از کار انداختن اگزیت، رله پس از برگشت آن خودش وصل می‌شود |
| حالت معکوس | ترافیک روی tls/raw/plain و وصل‌شدن دوبارهٔ اگزیت بعد از ری‌استارت رله |
| فوروارد UDP | ۴ پاسخ از ۴، مرزهای دیتاگرام برای هر اندازه از ۱ بایت تا ۶۰ کیلوبایت حفظ می‌شود، هر آدرس کلاینت استریم خودش را دارد و وقتی طرف مقابل عقب بیفتد دیتاگرام‌ها دور ریخته می‌شوند (هرگز صف نمی‌شوند)؛ تبادل Go ⇄ Python در هر دو جهت آزمایش شده |
| حامل `raw` روی هر دو موتور | رلهٔ Go ⇄ اگزیت پایتون و رلهٔ پایتون ⇄ اگزیت Go، هر طرف ۳ پاسخ از ۳؛ سمت Go با همان جدول پدینگ `simurgh/carriers.py` سنجیده می‌شود |
| تکه‌کردن ClientHello | با `split = 1` و `split = 3` روی یک اگزیت واقعی TLS: اولین سگمنت TCP روی سیم **دقیقاً n بایت** است (با یک پروکسی ضبط‌کننده جلوی اگزیت سنجیده شده) و تونل روی هر دو موتور بالا می‌آید — اگزیت دیگر یک قطعهٔ یک‌بایتی را با کاوشگر اشتباه نمی‌گیرد |
| آزمون سرتاسری هر حامل در Go | `go test ./...` یک رله + اگزیت + سرویس واقعی را روی `plain`، `tls`، `wss` و `raw` بالا می‌آورد: کاربر تکی با ۴۱ بایت / ۱۰۰ کیلوبایت / ۳ مگابایت و ۸ کاربر همزمان، بایت‌به‌بایت؛ ClientHello تکه‌شده (۱، ۳ و ۵۰۰ بایتی) هم ترافیک را جابه‌جا می‌کند |

## توسعه

```bash
git clone https://github.com/Dark-Sky07/Simurgh-Tunnel.git
cd Simurgh-Tunnel
python3 -m venv .venv && . .venv/bin/activate
pip install -e '.[secure]'
python -m pytest -q                 # ۱۹۰ تست (پایتون ۳٫۱۱)، بدون وابستگی تست‌اضافه
python tools/live_smoke.py          # می‌ریس زنده روی لوپ‌بک (۴۰ بررسی)

# موتور کامپایل‌شده (همان پروتکل، همان فایل‌های تنظیمات)
bash tools/build-go.sh              # باینری آمادهٔ ریلیز، وگرنه بیلد محلی
# نگه‌دارندگان پروژه: ساخت باینری‌های شش هدف ریلیز در dist/
bash tools/build-go.sh --release dist
cd go && go test ./...              # تست‌های carrier، mux و node + بردارهای RFC 8439
cd go && go test -race ./...        # همان‌ها زیر race detector
```

با انتشار GitHub Release، workflow در `.github/workflows/release-binaries.yml`
شش باینری و `SHA256SUMS.txt` را می‌سازد و پیوست می‌کند. برای افزودن فایل‌ها به
ریلیز موجود، اجرا کنید: `gh workflow run release-binaries.yml -f tag=v2.4.1`.

ساختار: `simurgh/protocol.py` (فریم‌ها و کدگذاری آدرس)، `mux.py` (مالتی‌پلکسر و
کنترل جریان)، `carriers.py` (چهار حامل) + `tlsio.py`/`obfs.py`/`decoy.py`،
`bridge.py` (اتصال سوکت ↔ استریم)، `exit.py` / `relay.py` (دو نقش)، `udp.py`،
`speedtest.py`، `panel.py` (پنل وب)، `menu.py`/`cli.py`/`systemd.py`،
`config.py`، `links.py` (لینک‌های اتصال)، `certs.py`.

موتور Go آینهٔ همین ساختار است: `go/internal/proto`، `mux`، `carrier`،
`node` (اگزیت + رله + UDP)، `bench`، `config`، `cmd/simurgh`. تنها کد
third-party آن به‌صورت vendor در `go/third_party/` است (ChaCha20-Poly1305 و
`x/sys/cpu` از `golang.org/x/*` با مجوز BSD-3-Clause، توضیح در
`go/third_party/README.md`) تا بیلد با `GOPROXY=off` روی ماشینی که به
`proxy.golang.org` دسترسی ندارد هم کار کند.
