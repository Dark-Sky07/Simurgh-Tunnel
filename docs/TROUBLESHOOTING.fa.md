# عیب‌یابی

[English](TROUBLESHOOTING.md) · **فارسی**

<div dir="rtl">

اول از همه عیب‌یاب داخلی را اجرا کنید — کانفیگ، توکن، فایروال، شنونده‌ها و لاگ را
بررسی می‌کند و راهنمای عملی می‌دهد:

```bash
simurgh doctor
simurgh logs -f          # لاگ زنده (/etc/simurgh/logs/*.log)
```

## پنل باز نمی‌شود

* پورت را باز کنید: `ufw allow 8787` (یا `firewall-cmd --add-port=8787/tcp`).
* وضعیت سرویس: `systemctl status simurgh-relay` یا `simurgh status`.
* پیش از v3.2.2 پیام `simurgh-relay: ok` فقط یعنی systemd دستور restart را
  پذیرفته است؛ ثابت نمی‌کند پروسه زنده مانده یا پورت 8787 را باز کرده است. نصاب
  و `simurgh update --restart` فعلی پاسخ واقعی `/healthz` روی loopback را لازم
  دارند و بدون آن خلاصهٔ موفقیت چاپ نمی‌کنند. روی نصب قدیمی، خطای واقعی استارت
  را این‌طور بگیرید:
  ```bash
  sudo systemctl status simurgh-relay --no-pager -l
  sudo journalctl -u simurgh-relay -n 60 --no-pager
  sudo tail -n 60 /etc/simurgh/logs/relay.log
  sudo ss -lntp | grep -E '(:8787|simurgh)' || true
  ```
* اگر لاگ `error: unrecognized arguments: --home /etc/simurgh` می‌دهد و unit در
  چرخهٔ `auto-restart` است، نسخهٔ v3.2.0 آرگومان سراسری را بعد از نقش نوشته است.
  نسخهٔ v3.2.1 هم generator را اصلاح می‌کند و هم ترتیب قدیمی را هنگام ارتقا
  می‌پذیرد. برای تعمیر فوری unit رله بدون تغییر کانفیگ:
  ```bash
  sudo sed -i 's#^ExecStart=/usr/local/bin/simurgh relay --home /etc/simurgh#ExecStart=/usr/local/bin/simurgh --home /etc/simurgh relay#' /etc/systemd/system/simurgh-relay.service
  sudo systemctl daemon-reload
  sudo systemctl restart simurgh-relay
  curl -sS http://127.0.0.1:8787/healthz
  ```
* آدرس و رمز پنل در اولین اجرا چاپ می‌شود و در `/etc/simurgh/state.json` ذخیره
  است؛ `simurgh status` هم نشانش می‌دهد.
* لینک یک‌بارمصرف صفحهٔ **امنیت** را ترجیح دهید. شکل قدیمی
  `http://<server>:8787/?k=<رمز-پنل>` هم کار می‌کند، ولی بلافاصله به `/` هدایت
  می‌شود تا رمز در نوار آدرس باقی نماند.

### داشبورد خالی یا خطای `429` غیرمنتظره در v3.2.2

در v3.2.2 چالش ناشناس HTTP Basic ممکن بود به‌اشتباه به‌عنوان رمز اشتباه شمرده
شود. در نتیجه پنج بازدید یا تازه‌سازی عادی می‌توانست مرورگر را ۳۰۰ ثانیه مسدود
کند و درخواست بعدی حتی با رمز درست، خطای `429 too many failed logins` بگیرد.
این نسخه همچنین با مقدار قدیمیِ view در `localStorage` ممکن بود همهٔ بخش‌ها را
مخفی کند، با غیرفعال‌بودن storage مرورگر اجرای داشبورد را متوقف کند و styleهای
داخلیِ خود پنل را از طریق CSP مسدود کند.

**به v3.2.3 ارتقا دهید.** در این نسخه فقط ارسال صریح اطلاعات ورود اشتباه به‌عنوان
تلاش ناموفق شمرده می‌شود؛ view ناشناخته به داشبورد برمی‌گردد، storage مرورگر
اختیاری است و styleهای پنل بدون اجازه‌دادن به اسکریپت داخلی اجرا می‌شوند. از پنل
احرازهویت‌شده مسیر **ابزارها → به‌روزرسانی‌ها → نصب به‌روزرسانی** را انتخاب کنید،
یا اجرا کنید:

```bash
sudo simurgh update --restart
```

ارتقا `/etc/simurgh`، pairing، مپینگ‌ها و رمزهای پنل را حفظ می‌کند؛ برای رفع این
خطای مرورگر کانفیگ را حذف نکنید. رمزهای واقعاً اشتباه در Basic و فرم ورود همچنان
rate-limit دارند.

### در v3.2.4 و قدیمی‌تر `/healthz` سالم است ولی داشبورد خالی می‌ماند

نصب پیش‌فرض با pip/venv ممکن بود همهٔ فایل‌های `simurgh/assets/` را جا بیندازد،
چون به‌عنوان package data برای setuptools اعلام نشده بودند. در این حالت
`/healthz` و صفحهٔ ورود می‌توانستند پاسخ بدهند، ولی `/app.css`، `/app.js`،
manifest و آیکن‌ها 404 بگیرند و رندر داشبورد احرازهویت‌شده اتصال را قطع کند.
اجرای پروژه از source checkout این نقص بسته‌بندی را نشان نمی‌داد.

**به v3.2.5 ارتقا دهید.** این نسخه هر هفت فایل پنل را در پکیج نصب‌شده قرار می‌دهد
و نصاب پیش از اعلام موفقیت، آن‌ها را با Python در حالت isolated بارگذاری و رندر
می‌کند. ارتقای عادی و غیرمخرب، کانفیگ و رمزهای موجود را حفظ می‌کند:

```bash
sudo simurgh update --restart
```

اگر updater نصب‌شده خودش نتواند ریلیز را پیدا کند، از پل نصاب در بخش بعد و بدون
`--force` استفاده کنید. بعد از ارتقا، فایل‌های واقعی پنل را بررسی کنید و فقط به
`/healthz` اکتفا نکنید:

```bash
curl -fsS http://127.0.0.1:8787/app.css >/dev/null
curl -fsS http://127.0.0.1:8787/app.js >/dev/null
```

این مسیرهای asset عمداً عمومی‌اند؛ داشبورد و APIها همچنان احرازهویت دارند. اگر
فایل‌ها محلی پاسخ بدهند ولی مرورگر از راه دور باز نکند، بررسی‌های سرویس،
شنونده، فایروال و SSH tunnel بالا را ادامه دهید.

## نصب روی `ensurepip`، build dependencies یا `ModuleNotFoundError` متوقف می‌شود

روی Ubuntu 22.04 تازه، نسخهٔ v3.2.6 و قدیمی‌تر ممکن بود ابتدا به‌خاطر نبودن
`python3.10-venv` نتواند venv بسازد. سپس pip برای build ایزوله می‌خواست نسخهٔ
جدیدتری از `setuptools` را از `files.pythonhosted.org` بگیرد؛ اختلال DNS یا مسیر
می‌توانست این مرحله را خراب کند و fallback مبتنی بر source هم ممکن بود با
`ModuleNotFoundError: No module named 'simurgh'` تمام شود.

**در v3.2.7 نصاب پیش از ساخت محیط، پکیج‌های کامل Python/venv/pip/setuptools/wheel
را از package manager سیستم نصب می‌کند.** metadata پروژه با setuptools 59.6 و
wheel 0.37 خود Ubuntu 22.04 سازگار است و ساخت Simurgh با
`--no-build-isolation --no-deps` انجام می‌شود؛ نصب اصلی به PyPI نیاز ندارد. venv
پکیج `cryptography` سیستم را هم می‌بیند و fallback نوع `.pth` دیگر جای نصب واقعی
پکیج را نمی‌گیرد.

یک بار همان نصاب واحد را بدون `--force` اجرا کنید:

```bash
curl -fsSL https://raw.githubusercontent.com/Dark-Sky07/Simurgh-Tunnel/main/install.sh | sudo bash
```

کانفیگ `/etc/simurgh`، رمزها و pairing حفظ می‌شوند. اگر مخازن خود APT/DNF/APK هم
در دسترس نیستند، ابتدا باید DNS یا مسیر مخزن اصلی شود؛ نصب پکیج‌های سیستم‌عامل بدون
یک منبع package manager سالم ممکن نیست. نصب اصلی v3.2.7 به PyPI وابسته نیست.

## ارتقا با خطای `GitHub answered 403` متوقف می‌شود

در v3.2.3 و نسخه‌های پیشین، کشف ریلیز فقط از `api.github.com` انجام می‌شود. IP
اشتراکی سرور ممکن است سهمیهٔ ناشناس API را مصرف کرده باشد، یا شبکه فقط hostname
مربوط به API را بسته باشد درحالی‌که صفحهٔ معمولی ریلیز گیت‌هاب در دسترس است.

v3.2.4 به ریدایرکت رسمی `/releases/latest` گیت‌هاب fallback دارد. مبدأ HTTPS و
مسیر تگ نهایی اعتبارسنجی می‌شود و سپس نشانی‌های مستقیم رسمی موتور و
`SHA256SUMS.txt` ساخته می‌شوند. نصب باینری همچنان checksum منطبق لازم دارد و
fallback امنیت بررسی را کم نمی‌کند.

فقط برای **این یک ارتقا از v3.2.3**، updater قدیمی نمی‌تواند اصلاح خودش را پیدا
کند. یک بار همان نصاب واحد را برای رسیدن به v3.2.10 اجرا کنید:

```bash
curl -fsSL https://raw.githubusercontent.com/Dark-Sky07/Simurgh-Tunnel/main/install.sh | sudo bash
```

`--force` اضافه نکنید و `/etc/simurgh` را حذف نکنید: اجرای عادی دوبارهٔ نصاب
pairing، مپینگ‌ها، رمزها و سایر تنظیمات را حفظ می‌کند. از v3.2.4 به بعد، پنل، منو
و `simurgh update --restart` همگی مسیر API همراه با fallback ریدایرکت را دارند.

## Pair با خطای `Connection refused` متوقف می‌شود

درخواست `/api/join` را **سرور گیرنده** می‌زند، نه مرورگر شما. بازبودن پورت تونل
ثابت نمی‌کند پورت پنل هم reachable است. لینک کامل Pair را در issue یا چت عمومی
نفرستید، چون رمز پنل داخل آن است.

۱. روی سرور **گیرنده**، همان آدرس پنل ارائه‌دهنده را مستقیم و بدون رمز تست کنید
   (IP و پورت را جایگزین کنید):

   ```bash
   curl --noproxy '*' -v --connect-timeout 5 http://OFFERING_PANEL_IP:8787/healthz
   ```

   پنل سالم JSON حاوی `"ok":true` برمی‌گرداند. `Connection refused` یعنی listener
   اتصال TCP را نپذیرفته یا فایروال آن را reject کرده؛ timeout بیشتر نشانهٔ
   مسیر/فیلترینگ است.
۲. روی سرور **ارائه‌دهنده** listener محلی را بررسی کنید:

   ```bash
   curl -fsS http://127.0.0.1:8787/healthz
   sudo ss -lntp | grep ':8787 '
   ```

   اگر loopback جواب می‌دهد ولی سرور دیگر نمی‌تواند وصل شود، فقط IP سرور گیرنده
   را در فایروال محلی و Security Group/فایروال ابری اجازه دهید:

   ```bash
   sudo ufw allow from RECEIVING_SERVER_IP to any port 8787 proto tcp
   ```

۳. لینک را دوباره با `IP/domain[:port]` **عمومی** سرور ارائه‌دهنده بسازید. روی دو
   سرور جدا نباید آدرس ضمنی `127.0.0.1`/`localhost` بماند، چون گیرنده به خودش وصل
   می‌شود. نسخهٔ v3.2.10 آدرس localhost تصادفی مرورگر را رد می‌کند، این تبادل را
   بدون proxy محیطی مستقیم انجام می‌دهد و endpoint پنلی را که خطا داده در پیام
   نشان می‌دهد.

## تونل بالا نمی‌آید (حالت مستقیم)

۰. اصلاً رله جفت شده؟ `simurgh status` (و پنل) روی سروری که پیش از اگزیتش نصب
   شده می‌گوید `not paired yet`. در صفحهٔ **Pair** اگزیت لینک راه‌اندازی بسازید
   و آن را در صفحهٔ **Pair** رله وارد کنید. نه نصب دوباره لازم است و نه CLI
   جفت‌سازی.
۱. روی **هر دو** سرور `simurgh doctor` را اجرا کنید.
۲. توکن باید بایت‌به‌بایت یکسان باشد (در صورت شک، لینک اتصال را دوباره بگیرید).
۳. پورت تونل باید روی **سرور خارج** باز باشد (مثلاً `443/tcp`) — همان پورتی که
   `[[listen]]` روی آن گوش می‌دهد.
۴. `simurgh status` روی رله: فیلدهای `last_error` و `bind_errors` می‌گویند آخرین
   مشکل چه بوده است.
۵. اگر اثرانگشت گواهی پین شده باشد، رله هر گواهی دیگری را رد می‌کند: در
   اگزیت لینک تازه بسازید و در صفحهٔ **Pair** رله از **Replace exit** استفاده
   کنید. فقط برای تشخیص می‌توانید موقتاً در `[exit]` مقدار
   `insecure_skip_verify = true` بگذارید و بعد بررسی گواهی را برگردانید.
۶. `strict_ports = true` روی اگزیت پورت‌هایی که به رله پیشنهاد نشده‌اند را رد
   می‌کند — پورت را به `push_ports` اضافه کنید یا سخت‌گیری را خاموش کنید.

## تونل بالا نمی‌آید (حالت معکوس)

در حالت معکوس **اگزیت به رله وصل می‌شود**، پس بررسی‌ها برعکس می‌شوند:

۱. روی رله: `dial = "exit"` در `relay.toml` باشد و پورت `[tunnel]` (مثلاً ۸۴۴۳)
   در فایروال باز باشد.
۲. روی اگزیت: لاگ باید `dialling the relay at <ip>:<port>` را نشان دهد؛ خطای
   `cannot reach the relay` یعنی آدرس یا فایروال اشتباه است.
۳. توکن اشتباه در هر طرف، بی‌صدا رد می‌شود و شنونده صفحهٔ طعمه را سرو می‌کند —
   توکن را بررسی کنید.
۴. اگر گواهی رله را عوض کرده‌اید، در پنل رله لینک تازه بسازید و دوباره در
   صفحهٔ **Pair** اگزیت وارد کنید تا fingerprint تازه شود؛ سپس اگزیت را
   ری‌استارت کنید.
۵. بعد از `systemctl restart simurgh-relay`، اگزیت در چند ثانیه خودش برمی‌گردد.

## تونل بالاست ولی اتصال فیلتر می‌شود

فیلترهای ایران خیلی وقت‌ها یک اتصال را از **اولین بستهٔ TCP** دسته‌بندی می‌کنند.
تانل جواب این کار را با `split` می‌دهد: بایت‌های اول دست‌دادن (هدر رکورد TLS،
`0x16 0x03 …`) در یک بستهٔ جدا می‌روند و بقیه حدود ۱۰ میلی‌ثانیه بعد می‌رسد، پس
فیلتری که حالت ندارد به‌جای یک ClientHello خوانا فقط یک قطعهٔ ناقص می‌بیند.

* نصب‌های تازه روی طرفی که dial می‌زند `split = 3` می‌نویسند (`[exit]` روی رله،
  `[[listen]]` روی اگزیت معکوس). با `grep -n split /etc/simurgh/relay.toml`
  ببینیدش.
* `simurgh install --split 0` (یا `simurgh init --split 0`، یا ویرایش خود فایل)
  خاموشش می‌کند — برای مسیرهایی که میدل‌باکس‌شان دست‌دادن تکه‌تکه را دور می‌ریزد.
* اگر طرف مقابل **نسخهٔ قدیمی** است (v2.0.0، پایتون) `split = 3` را نگه دارید:
  آن نسخه سه بایت را آغاز TLS می‌شناسد، ولی با قطعهٔ یک‌بایتی صفحهٔ طعمه را سرو
  می‌کند و تونل هیچ‌وقت بالا نمی‌آید. نسخهٔ فعلی و بعد از آن هر اندازه‌ای را
  می‌پذیرند.
* هزینه‌اش یک مکث ۱۰ میلی‌ثانیه‌ای در هر اتصال تونل است و بعد از آن هیچ: فقط
  اولین نوشتن دست‌دادن تکه می‌شود.

## یک پورت روی رله کار نمی‌کند

```bash
simurgh mapping list          # فعال است؟ bind شده؟
```

* سرویس باید روی `127.0.0.1:<target_port>` **روی سرور خارج** گوش بدهد (اگزیت به
  همان وصل می‌شود). اگر سرویس جای دیگری است، `--target-host 10.0.0.5` بدهید.
* مپینگ جدید را پنل بلافاصله اعمال می‌کند؛ CLI فقط «ذخیره شد» را چاپ می‌کند —
  اگر فایل را دستی ویرایش کرده‌اید `simurgh restart` بزنید.
* `simurgh mapping add` اگر پورت اشغال باشد هشدار می‌دهد؛ با
  `ss -ltnp | grep <port>` بررسی کنید.
* سرویس‌های UDP به `udp = true` نیاز دارند (`simurgh mapping add 2096 2096 --udp`).

## کاربران وصل می‌شوند ولی صفحه نمی‌گیرند

* روی رله تست کنید: `curl -v http://127.0.0.1:<iran-port>/` — اگر این کار کرد،
  تونل و اگزیت سالم‌اند و مشکل از سمت کاربر است (پورت/SNI اشتباه یا رد شدن توسط
  پنل).
* بعضی پنل‌ها فقط روی یک آدرس مشخص گوش می‌دهند؛ مطمئن شوید سرویس روی `127.0.0.1`
  (یا همان `target_host`) بالا است.
* پنل‌هایی که IP مبدأ را بررسی می‌کنند، `127.0.0.1` می‌بینند مگر `proxy_protocol`
  را روی اگزیت روشن کنید و پنل هم از PROXY protocol پشتیبانی کند.

## سرعت کمتر از انتظار است

```bash
simurgh speedtest        # اندازه‌گیری از داخل خود تونل
```

* به‌جای دست‌زدن به تک‌تک کلیدها از یک پروفایل شروع کنید: `simurgh tune speed`
  پنجره‌ها و تعداد اتصال‌های تونل را بالا می‌برد و `simurgh tune balanced` مقدارهای
  پیش‌فرض را برمی‌گرداند (بخش [پروفایل‌های کارایی](CONFIGURATION.fa.md#پروفایل‌های-کارایی-simurgh-tune)).
  روی لینک‌های خیلی پرسرعت (بیش از ۱ گیگابیت) همان `stream_window` مهم است
  (مثلاً `524288`) و `chunk = 65536` را دست نزنید.
* در `simurgh status` شمارندهٔ reconnect را ببینید: قطع/وصل‌های مکرر بیشتر از هر
  تنظیمی سرعت را کم می‌کنند.

## رله می‌گوید «پورت اشغال است»

پروسهٔ دیگری (یا نسخهٔ قدیمی) آن را گرفته است:

```bash
ss -ltnp | grep -E ':(443|8787)\b'
```

## نصاب در «writing the config…» می‌ماند

نسخه‌های قدیمی `install.sh` همان‌جا با `CONNECTIONS: unbound variable` می‌مردند و
در حالت پایپ (`curl … | bash`) خطای `BASH_SOURCE[0]: unbound variable` هم می‌داد.
اسکریپت را به‌روز کنید و دوباره اجرا کنید — نسخه‌های فعلی کانفیگ موجود را حفظ
می‌کنند و برنامه و unitهای systemd را تازه می‌سازند؛ لازم نیست چیزی پاک شود.
فقط `--force` صریح کانفیگ را جایگزین می‌کند و پیش از آن بکاپ زمانی می‌گیرد:

```bash
curl -fsSL https://raw.githubusercontent.com/Dark-Sky07/Simurgh-Tunnel/main/install.sh | sudo bash
```

اگر ردیابی خطا به `ModuleNotFoundError: No module named 'tomllib'` می‌رسد، حکایت
همین است روی پایتون ۳.۹/۳.۱۰ (دبیان ۱۱، اوبونتو ۲۰.۰۴/۲۲.۰۴): آن ماژول فقط از
پایتون ۳.۱۱ هست. نسخه‌های جدید خوانندهٔ TOML خودشان را همراه دارند
(`simurgh/_tomli`) و به PyPI نیازی نیست.

## «no compiled engine here; the portable python engine will be used»

این خطا نیست — هر دو موتور یک پروتکل دارند و هر نقش با هرکدام کار می‌کند. موتور
کامپایل‌شده به **Go 1.27 یا بالاتر** نیاز دارد (در `go/go.mod`)، و این از
`apt install golang-go` روی اوبونتو ۲۲.۰۴ (که Go 1.18 می‌دهد) جدیدتر است؛ پس نصاب
روی موتور پایتون می‌ماند. برای گرفتن موتور Go:

```bash
sudo bash /opt/simurgh-src/tools/build-go.sh    # اگر بتواند، Go را از go.dev می‌گیرد
sudo simurgh engine go
```

`tools/build-go.sh` وقتی نتواند بسازد دلیلش را چاپ می‌کند (نبود ابزار، ابزارِ
قدیمی‌تر از حد نیاز، یا بسته بودن مسیر `go.dev`).
